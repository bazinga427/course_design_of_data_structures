# 物流与供应链：问题定位（线路影响分析）设计说明

> 这个功能回答的不是"最多能运多少"，而是**"哪条线路出了问题、影响多大、该修哪条"**。
> 本文按"问题怎么建模 → 怎么算 → 怎么判定 → 界面怎么呈现 → 怎么验收"的顺序写，
> 可以直接作为答辩讲稿的底稿。

---

## 一、为什么要加这个功能

原来的供应链面板能算出"最大可交付量 19、瓶颈 4 条线路"，但它只能回答**现状**：

- 它不说"如果某条线路断了会怎样"；
- 它不说"这几条瓶颈线路里，哪条最要命"；
- 它不说"运力该投给谁"，也不说"哪条线路其实是白养的"。

于是加了**问题定位**：把"哪条线路出问题"从一句业务直觉，变成一个**可计算、可复现、可验证**的问题。

---

## 二、问题建模：四类"问题"对应四个可计算的量

| 业务上怎么说 | 数学上算什么 | 方法 | 改动前 |
| --- | --- | --- | --- |
| 现在最多能交付多少？ | 最大流 `F(G)` | 已有 | ✅ |
| 卡在哪几条线？（容量瓶颈） | 最小割的割集 | 已有 | ✅ |
| **哪条线坏了最要命？** | `F(G) − F(G 删掉 e)` | **逐条删除重算** | ❌ 新增 |
| **运力该投哪条线？** | `F(G 扩容) − F(G)` | **逐条扩容重算** | ⚠️ 只有单条版 |
| **哪条线是冗余的？** | 影响 = 0 的边 | 同上 | ❌ 新增 |

## 三、底层逻辑：反事实模拟 + 最大流最小割定理

### 3.1 反事实模拟（计算骨架）

对整个网络做一次最大流，只能得到"当前能运多少"。
要回答"某条线出问题会怎样"，就把那条线**改掉，重新算一次**：

```
影响(e) = F(当前图) − F(当前图删掉 e)        // 中断、减半：损失
影响(e) = F(当前图把 e 扩容) − F(当前图)      // 扩容：提升
```

这是在**完全相同的规则下做一次推演**，不是预测（不需要历史数据、不需要概率模型），
所以结论可复现——谁再算一遍都是同样的数。图论里这个问题叫**最核心边问题**（most vital edge），
逐条删除重算是标准暴力解法。

### 3.2 为什么"扩容只对瓶颈线路有效"是定理的必然

**最大流 = 最小割容量**。割是把源点和汇点分开的一组边，最大流的值等于"所有割里容量最小的那个"。

- 给一条**不属于任何最小割**的边加容量：任何割的容量都不会变小，所以最小值不变 → **最大流不变**；
- 反过来，**删**掉一条边却可能降低最大流——因为删除会切断路径，可能造出一个新的、更小的割。

所以"扩容"是理论可预测的（只对割边有效），"中断"必须逐条实算，不能从瓶颈线路推出来。

实测验证（示例图扩容 +5）：**4 条瓶颈线路各 +1，其余 15 条全部 +0**——理论和实验完全吻合。

这条"一重结论、两重证据"是本功能最值钱的地方：老师问"你的分析和课程内容有什么关系"，这就是答案。

### 3.3 为什么"最致命"≠"瓶颈"（实测的反直觉结论）

| 线路 | 容量 | 是最小割边？ | 中断后交付 | 影响 | 影响率 |
| --- | --- | --- | --- | --- | --- |
| **供应能力 → 华东工厂** | 14 | **否** | **8** | **−11** | **−58%** |
| 华东工厂 → 上海总仓 | 8 | 否 | 12 | −7 | −37% |
| 供应能力 → 华南工厂 | 10 | 否 | 12 | −7 | −37% |
| 上海总仓 → 苏州配送站 | 6 | 是 | 13 | −6 | −32% |
| 南京仓 → 宁波配送站 | 5 | 是 | 14 | −5 | −26% |
| 杭州配送站 → 上海门店 | 4 | 是 | 15 | −4 | −21% |
| 杭州配送站 → 杭州门店 | 4 | 是 | 15 | −4 | −21% |
| 宁波配送站 → 杭州门店 | 3 | 否 | 19 | **−0** | 0% |

三条结论：

1. **限流的是 4 条割边**（容量 6+5+4+4 = 19），它们决定"现在能运多少"；
2. **最脆弱的是「供应能力 → 华东工厂」**：它不在割集里，但一断交付量就从 19 掉到 8，
   因为华东工厂只有这一条上游线路——**单点依赖**；
3. **冗余的是「宁波配送站 → 杭州门店」**：断了完全不影响交付，可以整合运力。

**这就是为什么诊断必须同时给"限流榜"和"脆弱榜"。** 只看割集会漏掉真正的风险点。

### 3.4 最小割唯一性（本次实测）

枚举了示例图全部 1024 种割法：**最小割只有一个**（S = {1,2,3,4,5,7}，割边 4 条），
所以"瓶颈是哪几条"的结论是稳健的，不存在等容量的其他割法歧义。
（一般图可能存在多个等容量的最小割，那时程序返回的只是其中一个。）

## 四、计算流程

```
1. 先存下当前图的文本（exportGraphText）        ← 用于最后还原
2. 算一次基线最大流 F(s, t)，并记下割边集合
3. for 每条线路 e（上限 ANALYSIS_LIMIT = 300 条）:
     4. 构造改动后的图文本（buildGraphTextWithEdits）：
          中断     → 删掉这一行
          运力降级 → 容量 = max(1, floor(cap × 降级比例))   ← 降级比例可输入，默认 50%
          扩容     → 容量 = cap + N                        ← N 可输入，默认 +5
     5. core.loadText(改动文本) → core.maxFlow(s, t)
     6. 记录：情景后最大流、影响、影响率、是否割边、分级标签
7. core.loadText(原始文本) 还原        ← try/finally 保证一定执行
8. 结果缓存（情景 + 降级比例 + 扩容增量 + 源汇点 + 图规模 作为 key）
```

### 四个必须注意的实现坑（都是实测踩到的）

1. **容量不能填 0 来模拟中断**：文件解析会把 ≤ 0 的容量规范成 1，所以"中断"必须**删掉整行**。
2. **分析只能在"影子图"上做**：`loadText` 改的是核心里的图，所以不能调 `refreshSnapshot()`，
   否则界面上的图真的会被改掉。
3. **必须还原原始图文本**：否则存储结构、遍历、最大流这些功能会全部基于被改坏的图
   （代码里用 `try/finally` 强制还原，自检里也专门验证了这一点）。
4. **拼图文本时第一行必须是一行**：`n m directed` 拆成三行会让核心直接判定格式非法、返回 `ok:false`。

## 五、判定规则（把数字翻译成业务语言）

```
影响率 = 影响 / 基线        例：11 / 19 = 58%
```

| 影响率 | 判定 | 业务含义 |
| --- | --- | --- |
| ≥ 40% | 🔴 致命 | 单点风险，断了供应链基本瘫痪 |
| 10% ~ 40% | 🟠 敏感 | 需要备份通道 |
| 0 < 影响率 < 10% | 🟡 轻微 | 可接受，注意监控 |
| = 0 | ⚪ 冗余 | 可砍掉或当备份 |
| 扩容后提升 > 0 | 🟢 建议扩容 | 投入有效 |
| 扩容后提升 = 0 | ⚫ 扩容无效 | 不在最小割里，投入无效 |

另有一个**独立标记**：该边在当前最小割割集里 → 附加「瓶颈」标签
（所以会出现"敏感 · 瓶颈""建议扩容 · 瓶颈"这类组合标签，正好体现"限流"和"脆弱"是两回事）。

阈值写在 `src/domain/supplyChain.js` 顶部的 `IMPACT_THRESHOLDS` 里，是**可调常量**，不是写死的魔法数字。

排序规则：影响降序，影响相同按容量升序。默认只显示有影响的线路，可一键"展开全部"。

## 六、数据契约（前后端/模块之间的接口）

### 6.1 `buildGraphTextWithEdits(graph, edits)`

```js
/**
 * 按 edits 改一张图的文本（现有 buildGraphTextWithExtraCapacity 的泛化版）。
 * @param {object} graph  核心快照（graph.edges = [{u,v,cap}]）
 * @param {Array<{u:number, v:number, cap:number|null}>} edits
 *        cap === null 表示删掉这条边（模拟中断）；数字表示改容量
 * @returns {string} 可直接喂给 core.loadText 的图文件文本
 */
```

### 6.2 `analyzeLineImpact(core, graph, meta, options)`

```js
/**
 * options: { originalText, mode:'fail'|'degrade'|'expand', delta, ratio, source, sink, limit }
 *   mode='fail'    中断（删除该边）
 *   mode='degrade' 运力降级，ratio 是保留比例 0.01~0.99（0.5 = 运力减半，可输入）
 *   mode='expand'  扩容，delta 是增量（可输入）
 * 返回:
 * {
 *   ok, error?, mode, delta,
 *   base,          // 基线最大流
 *   demand, gap,   // 需求 / 缺口
 *   unit,          // 业务单位（示例里是"单位"）
 *   cutKeys,       // 当前瓶颈线路的 key 列表
 *   rows: [{
 *     key, u, v, cap, label,   // 线路信息（label 是业务名称）
 *     after,                   // 情景后的最大流
 *     impact,                  // 影响大小（非负数）
 *     rate,                    // 影响率 0~1
 *     direction,               // 'loss' | 'gain' | 'none'
 *     isCut,                   // 是否最小割割边
 *     level,                   // 'fatal'|'sensitive'|'minor'|'none'|'gain'|'gainNone'
 *     tag                      // 展示用中文标签，如 "敏感 · 瓶颈"
 *   }],
 *   summary: { worst, affected, redundant, fatalCount, sensitiveCount, redundantCount },
 *   truncated                // 线路太多时是否只算了一部分
 * }
 */
```

**设计取舍**：判定逻辑（阈值、分级、标签、结论）全部放在 `src/domain/supplyChain.js`，
不放组件里。理由和项目已有的 `buildSupplyChainSummary` / `supplyChainSentence` 一致：
**纯函数才能被自检直接覆盖**，组件只负责展示。

## 七、界面与交互

位置：供应链面板末尾（"关键线路利用率"之后），面板本身在内部滚动。

```
┌─ 问题定位 · 线路影响分析 ────────────────────┐
│ 情景 [中断] [运力降级] [扩容]                    │
│ 降级至 [50] %   扩容 + [5]      [重新分析]        │
│ 基线可交付 19 │ 需求缺口 5 │ 瓶颈线路 4          │
├──────────────────────────────────────────────┤
│ 供应能力 → 华东工厂      致命   容量 14 → 情景后 8   -11（-58%） │
│ 华东工厂 → 上海总仓      敏感   容量  8 → 情景后 12   -7（-37%） │
│ 上海总仓 → 苏州配送站  敏感·瓶颈 容量  6 → 情景后 13   -6（-32%） │
│ …                                             │
│ [展开全部 19 条]  点一行可以在画布上高亮这条线路    │
├──────────────────────────────────────────────┤
│ 结论 · 当前最大可交付 19 单位，缺口 5 单位        │
│ 风险最高的是「供应能力 → 华东工厂」：中断后可交付量 19 → 8，│
│ 影响 -11（-58%）。它不在瓶颈线路里，说明这里存在单点依赖，│
│ 建议增加备用通道。                              │
│ 共 1 条致命、17 条敏感、1 条冗余线路（判定口径：…）。│
└──────────────────────────────────────────────┘
```

交互设计：

- 点情景按钮 → 立即重算（同情景 + 同图命中缓存，不重复跑）；
- **情景参数可输入**：「降级至 X%」和「扩容 +N」都是输入框（默认 50% 和 +5），
  在当前情景下改完按回车或离开输入框就会自动重算，改另一个情景的参数只记下来、
  等切过去时使用；输入值会被收进合法范围（降级 5%~95%，扩容 1~999）；
- 载入供应链示例后**自动跑一次**（默认情景"中断"），不用手动点；
- 点表格里任意一行 → 画布上该线路变成**橙色粗虚线**（`risk` 类，和粉色割边区分），再点一次取消；
- 退出场景、换图、改源点/汇点 → 自动清空分析结果，避免展示过期数据。

## 九、复杂度与局限（答辩追问备用）

| 追问 | 回答 |
| --- | --- |
| 计算量多大？ | `O(m × 一次最大流)`。示例图 19 条线路是瞬间完成；代码里限制最多 300 条，超过就截断并提示。 |
| 有更快的算法吗？ | 有。理论上可以用 Gomory-Hu 割树或在敏感度分析上做文章；课程设计规模没必要。 |
| 一次只坏一条线，两条同时坏呢？ | 只做了单点故障（single failure）。多故障是 C(m,2) 级增长，属于后续扩展。 |
| 换源点/汇点结果会变吗？ | 会，结论是相对于当前 s/t 的，所以改了源汇点就自动清空重算。 |
| 最小割唯一吗？ | 不一定。本次实测示例图枚举了全部 1024 种割法，最小割唯一。 |
| 为什么不直接用割集当"关键线路"？ | 割集只反映容量限制；实测里最脆弱的「供应能力→华东工厂」并不在割集里，所以必须额外做中断模拟。 |

## 十一、答辩口述稿（约 3 分钟，可直接照讲）

> 这个功能叫"问题定位"，它回答的是：**哪条线路出了问题、影响多大、该修哪条**。
>
> 底层逻辑是**反事实模拟**：把供应链建成有向带容量图，"最多能交付多少"就是最大流。
> 要问"这条线断了会怎样"，就把这条线删掉重新算一次最大流，差值就是它的影响。
> 整个过程是在"影子图"上做的，算完会把原图还原回来，所以不会污染界面上正在看的图。
>
> 这里有一个数学上的必然：最大流等于最小割的容量。所以给一条**不在最小割里**的边加容量，
> 最大流根本不会变。我们实测扩容 +5 单位，只有 4 条瓶颈线路各提升了 1，其余 15 条全都没变化——
> 理论和实验正好对上。
>
> 但最有意思的是"瓶颈"和"脆弱"是两回事。实测下来最脆弱的是「供应能力 → 华东工厂」，
> 它一断交付量就从 19 掉到 8，降了 58%；可它**并不是**瓶颈线路。
> 原因是华东工厂只有这一条上游线路，属于单点依赖。
> 所以我们的报告同时给两个榜单：限流的（割集）和脆弱的（中断影响），再加上该投入的和冗余的。
>
> 最后把这些数字按影响率分级——超过 40% 算致命、10% 到 40% 算敏感、等于 0 算冗余——
> 自动生成一句话结论，点表格里任意一行还能在画布上把那条线路高亮出来。
> 降级比例和扩容增量都可以自己输，比如"运力降到 20%"或者"扩容 +20"，结果会立刻重算。
> 这套分析逻辑有自检覆盖，一共 108 项断言，其中包括"分析跑完必须把图还原"这条回归。

## 十二、附：一句话备忘

- 计算本质：**改一条线 → 重算最大流 → 和基线对比**
- 理论依据：**最大流 = 最小割**（扩容只对割边有效；中断必须实算）
- 安全底线：**影子图 + try/finally 还原**
- 判定口径：**影响率 40% / 10% 两级阈值 + 割边附加标记**
- 交付物：**限流榜、脆弱榜、投入榜、冗余榜 + 一句话结论 + 画布定位**
